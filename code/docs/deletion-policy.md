# 酒店与账号删除的需求一致性说明

REQ-001明确“管理员管理酒店与账号”，需求没有禁止管理员移除酒店或账号。因此增加删除入口与该职责一致，是本次用户明确提出的管理功能补充。

REQ-008、REQ-019要求保留已发生入住与费用，REQ-020要求操作可追溯，REQ-021要求历史统计不重不漏，REQ-025要求已确认订单持久保存。因此实现采用逻辑删除：记录删除人、删除时间，从日常管理/可选列表移除，保留原始对象及其历史关联，不级联清除订单、来宾、费用或日志。

| 对象 | 删除后的行为 | 删除前的限制 |
| --- | --- | --- |
| 酒店 | 从酒店管理、候选查询及维护选项移除；房源停售，旧报价不能新订；历史订单仍可读取，报表保留“已删除·历史”酒店筛选项 | 不存在预订中、已确认、已入住、待安置订单；不存在待安置或待核对/争议费用；须先处理有效工作人员账号绑定 |
| 账号 | 从账号列表移除并禁用，不能重新登录，已有会话访问业务时也失效；保留历史责任归属、来宾资料和日志 | 不能删除当前登录账号或最后一个有效管理员；无处理中请求；接待人员无未完成负责订单和费用；有在办订单的酒店须保留其他有效工作人员 |

“停用”继续保留在账号编辑中；已删除账号不能通过编辑重新启用，原账号名继续保留，防止同名新账号继承旧会话或历史身份。新账号可使用不同账号名重新绑定同一来宾。

前端提供明确对象名称的确认弹窗，删除失败时显示具体业务原因。服务端独立检查管理员权限、当前版本和关联业务，不能通过修改请求绕过。两个删除接口均要求CSRF及稳定请求标识，重复提交返回原结果，操作日志记录目标对象与请求编号。

接口：`DELETE /api/admin/hotels/{id}`、`DELETE /api/admin/users/{id}`；请求体为当前对象的 `version`。

账号生命周期操作与业务命令共用账号锁；管理员按编号锁定，避免并发互删后失去全部管理员。业务写事务采用READ COMMITTED，在取得账号/酒店锁后重新检查业务，避免使用等待加锁前的旧快照执行删除。

数据库迁移为 `V3__hotel_and_account_deletion.sql`，仅增加删除标记列和索引，不清空已有数据。使用更新后的JAR重新启动时由Flyway自动升级。

当前版本为 1.1.0，可打开 [桌面程序](../release/CampusHospitality.exe) 或双击 `start.cmd`。

本说明是本次新增功能的实现规则，不将其伪称为原27条已确认需求中的逐字规定。
