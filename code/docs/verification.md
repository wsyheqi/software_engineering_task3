## 后端验证场景

1. 多晚、多房型的一项不足导致整单失败，不残留其他明细占用。
2. 名额变化但仍够需要重新确认，并保留不可变的请求结果；确认后改价不追改原价。
3. 同一请求6个并发提交仅一份订单和占用。
4. 两个接待范围并发争用最后一间，只有一笔成功。
5. 18:00整取消按各间房锁定首晚价收取记录，重复取消不重复释放。
6. 17:59:59取消费用为零。
7. 新方案不足，改订失败时原订单及占用不变。
8. 特殊改订缺少任一方批准均不生效；双方确认后才可执行，不能恢复终态订单。
9. 首人入住与后续补登记分开，重复登记无第二事实，跨酒店拒绝。
10. 到店提醒不自动登记未入住；保留期内拒绝，期后酒店登记，晚到不能恢复原单。
11. 停业替代失败保留原占用；成功时原子关联新单、关闭释放原单，停售仍保留。
12. 已入住停业保留实际4间夜，新单只接剩余2间夜；邮件失败不撤销安置。
13. 来宾响应不含协议价和他人资料；管理员默认电话脱敏；缺少CSRF校验拒绝写请求。
14. 非正预算拒绝，低于70分与未审核酒店排除。
15. 续住用新增日期申请价，不追改已住晚价，续住失败保留原住宿。
16. 提前退房释放未来日期；额外费用争议独立处理，不混入实住间夜费用。
17. 维修冲突转待处理，不覆盖既有占用；协调后才能扣减。
18. 业务评分示例得到59分。
19. 下单日期口径按创建日选单，关联的住宿日期可在未来。
20. 已持久化PENDING命令可恢复，原请求重试不重复占用。
21. 日期等输入格式错误会结束为可查询的拒绝结果，不残留PENDING请求或部分入住事实。

## 实现取舍与验收边界

- 默认本地演示使用 H2 文件模式，生产配置使用 MySQL；都通过 JDBC、Flyway、数据库唯一键及事务执行同一套业务逻辑。H2根记录使用排他锁，MySQL普通业务使用共享锁、停业和资格维护使用排他锁。H2设置 `WRITE_DELAY=0`，关闭提交后日志刷新延迟，设置依据见[H2命令文档](https://h2database.com/html/commands.html#set_write_delay)。
- 模块以主要服务组织，统一接口适配、命令幂等和事务模板复用。状态机和需求对象单独建模。没有为每层生成空实现类，也没有引入额外分布式系统。
- Web会话保存在服务端进程，重启后重新登录。业务请求及结果存在数据库，可以重新登录后按原标识查询；浏览器仅持久化待查请求编号，不存登录令牌或完整业务参数。
- 报表中非住宿费用按登记日期归属；待核对或有争议的费用单列。下单口径按创建日期选单，图表横轴仍为这些订单的住宿晚。来宾实际到店不自动等同于全部房间已使用。
- 未入住提醒与通知首期采用站内渠道；停业通知同时生成站内和学校邮件任务。未配置学校SMTP时如实进入失败跟进，不能把演示环境的任务创建当作真实邮件已送达。
- 当前环境没有运行中的Docker服务，未执行MySQL容器验收。尚未接通真实学校邮箱，也未完成需求指定的4核8GB、50家酒店、1万历史订单、100人并发性能测试，以及服务器重启和网络中断的完整恢复演练。上述项目仍须在对应环境验收。

此处的应用进程重启核对是有限的本地持久性检查，不代表已经验证全部故障条件或全部非功能需求。
